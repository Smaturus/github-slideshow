# Род Матюхиных и Скиба — семейный архив

**Live:** https://smaturus.github.io/github-slideshow/

Статический генератор семейного архива: локальный GEDCOM-экспорт, проверенные архивные дополнения и редактируемые тексты преобразуются в сайт с летописью, ономастикой, географией и SVG-древом. Подробнее о разделении слоёв — в разделе [Источники данных](#источники-данных).

---

## Возможности

- **Летопись** — четыре родовые линии, таймлайн поколений, блок «точка встречи» двух ветвей
- **Ономастика и география** — частые фамилии и места рода с пояснениями
- **SVG-древо** — прямые предки с пометками «подтверждено / гипотеза / нет данных»
- **Карта поиска** — приоритетные «белые пятна» в прямой линии
- **Редактируемые тексты** — заголовки и абзацы в `content/content.yaml` без правок Python

---

## Источники данных

Опубликованные сведения складываются из трёх слоёв. Слои различаются способом получения и степенью доказанности, поэтому разделены и в коде, и в подаче на сайте.

**1. Структурированная основа — GEDCOM.** `data/skiba.ged` — локальный экспорт семейного древа в формате GEDCOM 5.5.1; типичное происхождение файла — выгрузка проекта MyHeritage. Это основной машиночитаемый вход генеалогических данных: `scripts/parse_gedcom.py` берёт из него персоны, даты, места и родственные связи, а `build_site.py` считает по ним статистику, таймлайн поколений, ономастику и географию. MyHeritage при этом — только обычный источник самого файла, а не инстанция, удостоверяющая содержание: ссылки внутри экспорта в основном ведут на Smart Match, то есть на деревья других пользователей, а не на архивные документы (это прямо оговорено в разделе «Источники и оговорки» на сайте).

**2. Архивные дополнения — то, чего в GEDCOM нет или что там неполно.** Часть предков установлена вне выгрузки, по постранично отснятым архивным делам — прежде всего по ревизской сказке 1834 года по селу Мокрое Белевского уезда Тульской губернии (двор №26). Распознавание скорописи на снимках страниц и сопоставление записей выполнялись с помощью ИИ (OCR и разбор рукописного текста); прочтения проверялись вручную и лишь затем кодировались в сборку — двумя разными путями:

- **персоны и связи** — программной вставкой в `scripts/parse_gedcom.py` (блок «Inject … from the 1834 Revision List»). Илья Матвеев, Григорий Ильин, их жёны и дети создаются в модели данных с собственными идентификаторами (`@I_MOKROE_*`, `@F_MOKROE_*`), а Федот (`@I155@` в GEDCOM) переподключается к найденным родителям. Сам `data/skiba.ged` при этом не правится.
- **формулировки и оговорки** — текстами в `content/content.yaml`: очерк линии Матюхиных с реквизитами дела, примечания к фамилиям и местам, легенда «подтверждено / гипотеза / нет данных».

ИИ и OCR здесь — исследовательский инструмент чтения источника, а не самостоятельный источник и не автор выводов. Ответственность за опубликованные генеалогические утверждения остаётся за проектом: чтения, не подтверждённые документом, помечены на сайте как гипотезы; фамилия Матюхин для поколений 1834 года сознательно не утверждается, потому что в ревизии она не записана.

**3. Редакционный слой — YAML.** `content/content.yaml` отвечает за подачу: заголовки, вводные абзацы, очерки линий, примечания, подписи и легенду. Числа, даты и цепочки поколений в нём не дублируются — их считает генератор из слоёв 1 и 2.

Правила приватности применяются к первому слою: GEDCOM содержит данные ныне живущих людей, и публикация ограничивается генератором (см. [Приватность](#приватность)). Вставленные архивные персоны — люди XVIII–XIX веков, под ограничение не попадают.

## Архитектура

```
ревизская сказка 1834 г. (снимки страниц, вне репозитория):
чтение (OCR + ИИ), проверка ─┐
                             ▼
data/skiba.ged          ──►  parse_gedcom.py  ──┐
  (локально, не в Git)                          ├──►  build_site.py  ──►  index.html
content/content.yaml    ────────────────────────┘         ▲
assets/site.css         ──────────────────────────────────┘
                                                          │
merge в master ──► GitHub Actions ──► gh-pages ──► GitHub Pages
                                      (только index.html, .nojekyll
                                       и assets/hero-bg*.{avif,webp,jpg})
```

## Инженерные решения

**Разделение данных и текстов.** GEDCOM и проверенные архивные дополнения формируют факты в Python, а `content/content.yaml` содержит только редакционные тексты. Архивные персоны добавляются отдельным кодовым слоем, поэтому исходный GEDCOM можно заменить новым экспортом без ручного редактирования.

**Валидация YAML.** `build_site.py` проверяет обязательные ключи и типы в `content/content.yaml` и падает с понятным сообщением, если структура нарушена.

**Осознанный trade-off.** Сборка не выполняется в CI: GEDCOM содержит персональные данные и остаётся локально. Перед merge в `master` обновлённый `index.html` коммитится вручную после локальной пересборки.

## Технологии

- Python 3, PyYAML; GEDCOM 5.5.1 и вручную проверенные архивные дополнения
- Статический HTML, CSS и SVG
- GitHub Actions и GitHub Pages

## Быстрый старт

```bash
# 1. Положите экспорт MyHeritage в data/skiba.ged (файл не коммитится)
mkdir -p data
cp /путь/к/экспорту.ged data/skiba.ged

# 2. Установите зависимости и соберите сайт
python3 -m pip install -r requirements.txt
python3 scripts/build_site.py

# 3. Локальный просмотр
python3 -m http.server 8080
# → http://localhost:8080
```

Архивные поколения добавляются в `scripts/parse_gedcom.py`, поэтому замена GEDCOM не удаляет их автоматически.

### Редактирование текстов

1. Правки в `content/content.yaml`
2. `python3 scripts/build_site.py`
3. Коммит `content/content.yaml` и `index.html` → merge в `master`

---

## Публикация

После merge в `master` workflow [`.github/workflows/pages.yml`](.github/workflows/pages.yml) автоматически обновляет `gh-pages`, публикуя только `index.html`, `.nojekyll` и оптимизированные варианты `assets/hero-bg*`. GEDCOM, YAML, Python-скрипты и исходные изображения на сайт не попадают.

**Требования к репозиторию (один раз):**

- `Settings` → `Actions` → `General` → **Read and write permissions** для workflow
- Ветка `gh-pages` не должна блокировать force-push от GitHub Actions

## Структура репозитория

| Путь | Назначение |
|------|------------|
| `data/skiba.ged` | GEDCOM-экспорт (основной источник данных), локально, в Git не попадает |
| `content/content.yaml` | Редактируемые тексты сайта |
| `scripts/parse_gedcom.py` | Парсер GEDCOM, модель персон, фильтрация приватности, вставка предков по архивным находкам (ревизия 1834 г.) |
| `scripts/build_site.py` | Генератор `index.html`: `render_*` секции, валидация YAML, post-build проверка |
| `assets/site.css` | Стили (инлайнятся в HTML при сборке) |
| `assets/Image 1.png`, `assets/Image 2.png` | Мастер фона первого экрана и референс раскладки (в Pages не публикуются) |
| `assets/hero-bg*.{avif,webp,jpg}` | Оптимизированные производные фона первого экрана — входят в allowlist `gh-pages` |
| `index.html` | Собранный сайт (коммитится в `master`) |
| `requirements.txt` | Python-зависимости |
| `.github/workflows/pages.yml` | Автопубликация в `gh-pages` |
| `.nojekyll` | Отключает обработку Jekyll на GitHub Pages |

## Приватность

GEDCOM содержит персональные данные ныне живущих людей и не хранится в репозитории. Для живых публикуются только имя и год рождения; точные даты, места и контакты исключаются. Человек без года рождения и отметки о смерти считается живым. Правила опираются на дату экспорта GEDCOM, а сборка проверяет итоговый HTML на утечки.
